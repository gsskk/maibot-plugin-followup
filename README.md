# followup_window:被 @ 后的跟进窗口(MaiBot 插件)

群里有人 @ 麦麦(或引用回复麦麦的消息)之后,接下来几分钟里的追问往往不再带 @。
MaiBot 群聊的动态门控(`reply_trigger_mode = "dynamic"`)偏偏在这时最紧:一次 @ 强制回复要占掉一大块额度,
后续不带 @ 的消息最难进入 Planner。本插件在被 @ 后开一个跟进窗口,记下这次对话的参与者;
窗口里参与者的追问到来时,把该群有效发言频率临时拉到 1.0 约 5 秒,让那一批进 Planner,由它照常决定回不回、怎么回。
别人之间的闲聊照常走门控,不会因为窗口开着就被放进来。插件只看「谁发的、有没有 @ 或引用回复麦麦」,不看内容,
不强制回复,不改写消息。

窗口只在麦麦自己发言或再被 @ / 引用回复时续期,并且有上限;群友说话不续期,热闹的群不会一直处于活跃态。

**为什么只认参与者。** 早期版本在窗口里放行每一批消息,实测开窗后两分钟内麦麦对群友之间的闲聊也接了话:
窗口把门控整个放开后,「与我有关」只剩 Planner 的提示词在约束,随机性太大。按参与者筛选是结构性的,不靠模型听话。

**为什么提频时一律拉到 1.0,而不是按倍数调高。** 门控对频率的反应是断崖式的:频率低于某个值时 @ 之后剩余额度为 0,
调高了也和没调一样;中间值放行哪一批取决于概率排序,不带问号、不带名字的追问恰好排在后面。
所以克制靠时长(窗口时长、活跃上限可按群覆盖)和名单,不靠降低频率。

## 行为

- 有人 @ 麦麦,或引用回复麦麦的消息 → 该群(在范围内时)进入活跃态,持续 `window_seconds`,发消息的人成为参与者。
  叫名字、麦麦自己发言(包括主动插话、其他插件的推送)都不开启。私聊没有门控,不处理。
- 开窗本身不改频率:宿主对 @ 本就强制回复,别人的消息照常走门控。
- 活跃态里参与者发来一条不带 @ 的消息,或任何人不带 @ 地引用回复麦麦 → 频率临时拉到 1.0,保持 5 秒后恢复;
  这段时间里又来一条同类消息,就从那时起再保持 5 秒。
- 活跃态里有人 @ 或引用回复麦麦 → 这个人也成为参与者。
- 活跃态里麦麦在该群成功发出一条消息,或再次被 @ / 引用回复 → 截止时间重设为「现在 + `window_seconds`」,
  但不超过「本次活跃态开始 + `max_active_seconds`」。
- 到期后一秒左右退出;正在提频的恢复为 1.0。插件卸载或被禁用时所有活跃群立即恢复。
- 改配置把某群移出范围(进黑名单、或不在白名单里)时,该群已开的窗口立即退出;改时长只影响之后的开窗与续期。
- 不持久化:重启 MaiBot 后所有窗口消失,频率回到宿主默认。
- 群被刻意静音(talk_value 为 0)时不提频;talk_value 本来就 ≥ 1.0 时无需提频。

## 安装

要求 MaiBot 1.3.x、`maibot-plugin-sdk` 2.15.x–2.16.x;插件没有额外 Python 依赖。

### 方式一:官方插件市场(推荐)

接入官方插件库后,在 MaiBot WebUI 的「插件扩展」中搜索 **被 @ 后跟进窗口** (或 `gsskk.followup-window`),点击安装即可。

### 方式二:手动安装

将本仓库克隆或复制到 MaiBot 的 `plugins/followup_window` 目录下:

```bash
git clone https://github.com/gsskk/maibot-plugin-followup /path/to/MaiBot/plugins/followup_window
```

然后在 WebUI 的插件配置页(或 `plugins/followup_window/config.toml`)把「启用插件」`plugin.enabled` 打开,重启 MaiBot。
插件默认关闭,与 hermes_bridge 一致,需要显式开启。

## 配置

```toml
[plugin]
enabled = true

[followup]
scope_mode = "all"          # all | blacklist | whitelist
groups = []                 # blacklist 模式下关闭的群号,whitelist 模式下开启的群号;all 模式忽略
window_seconds = 300        # 被 @ 或麦麦发言后,活跃态再持续这么久
max_active_seconds = 900    # 一次活跃态从开始算最长多久

# 按群覆盖时长,留 0 或不写的项沿用上面的默认
[[followup.group_overrides]]
group_id = "123456789"
window_seconds = 120
max_active_seconds = 120    # 等于 window_seconds 即不续期:窗口只开一次 120 秒
```

- 群号写裸群号,不带平台前缀;加不加引号都行。
- 填错的值不会让配置失效:未知的 `scope_mode` 按 `all` 处理,非正数的时长回落到默认值;
  `max_active_seconds` 小于 `window_seconds` 时按 `window_seconds` 算。这些问题在启用时以
  `[followup] 配置问题:` 的 WARNING 打进日志。
- talk_value 压得很低的群(例如 0.01)提频时也一样拉到 1.0;不希望那里接追问,就缩短它的时长或放进黑名单。

## 怎么看它在工作

插件日志都带 `[followup]` 前缀,每次进入、续期、提频、提频结束、退出各一行:

```bash
grep '\[followup\]' /path/to/MaiBot/logs/<当天日志>
```

- `[followup] 进入(@|引用) 群 … 参与者=… 截止=… 上限=…`:开窗。
- `[followup] 续期(发言|@|引用) 群 … 参与者=N 截止=… 已持续=…s`。
- `[followup] 提频(参与者|引用) 群 … base=0.400 系数=2.500 至=…`:base 是去掉插件系数后的原始 talk_value。
- `[followup] 提频结束 群 … 系数=2.500→1.0`。
- `[followup] 退出(到期|卸载|禁用|移出范围) 群 … 参与者=N 累计=…s`。
- `[followup] … 写入系数未生效 … 放弃这次提频`:多见于重启后某群的第一条就是不带 @ 的引用回复,宿主还没建出该群的会话,
  约 4 秒内尝试 5 次仍失败;下一条同类消息会再试。
- `[followup] 群 … 恢复系数失败`:恢复 1.0 的调用失败,每秒重试,12 次仍失败会打「放弃」;
  此时该群系数可能仍偏高,直到下一次提频或重启。

宿主每收到一次系数写入都会立即对待处理的消息跑一次门控,所以「提频」「提频结束」(以及写入重试的每一次)
之后紧跟着会多一条门控判定,这是正常的,不代表来了新消息。

对照宿主「回复调度 … 动态门控」日志:参与者的追问批次应为 `频率=1.000`、阈值 0.00、进入 Planner;
同一窗口里别人的消息仍是原来的频率(例如 `频率=0.400`),照常判定。

## 已知限制

- **空闲退避仍生效。** Planner 连续两次以「不回复」结束一轮后,群聊进入 15 秒起、倍增、上限 300 秒的退避,
  它在门控之前判断,所以活跃态里的反应可能慢十几秒。
- **与其他写频率的插件冲突。** 宿主的频率调整系数每个会话只有一个值,后写覆盖先写;
  同时启用别的调频率插件会互相覆盖。
- **只认参与者的代价。** 提频的 5 秒内,同一群别人到达的消息也会被放行;A @ 了麦麦、B 不带 @ 接着追问同一话题时,
  B 的消息走原门控,可能接不住;参与者自己和别人闲聊的消息也会放行,由 Planner 决定回不回。
- **空闲退避可能吞掉一次提频。** 退避把参与者那一批的判定推迟到提频结束之后时,这一批按原门控处理。
- **门控统计不清零。** 活跃态里的回复照常计入动态门控的一小时窗口,退出后门控会比平时更紧一段时间。
- **focus_mode。** 开启时宿主有效频率恒为 1.0,本插件无意义但无害。

## 更新

- **插件市场安装:** 在 WebUI 插件市场中点击更新。
- **手动安装:** 在 `plugins/followup_window` 下执行 `git pull` 并重启 MaiBot。
  也可以重新复制仓库文件覆盖后重启。

```bash
grep '\[followup\] 已加载' /path/to/MaiBot/logs/<当天日志>   # 版本号应与 _manifest.json 的 version 相同
```

插件源码目录里没有 `config.toml`,覆盖与更新不会动现有配置。
